# Flight log: bulk edit and filtering

## Bulk update

- **Bulk update — landed** (all five steps below). Select rows in the Flights view, "Edit N flights…", switch on the fields to change. The notes record why each piece is shaped as it is. Follow-ups, none started: **bulk delete** (with `showUndo` as a deferred commit — hide, then delete when the toast expires — since an apply-then-reverse undo would need a verbatim restore path).
  - **Step 1 landed: row selection in `ViewFlightLog`.** Hover-revealed checkbox column in the table layout (Mail-style: every row shows its box once anything is selected; always shown under `hover: none`; opacity rather than visibility so keyboard focus can reveal it), shift-click ranges, a select-all that covers *visible* rows only, Esc / "Clear selection" (Esc only when nothing on top took it: an `NcActions` menu and the `FilterPicker` editor close and call `preventDefault`, which the view checks; a dialog closes without it, so a visible `.modal-mask` — the test `@nextcloud/vue`'s hotkeys use — also stands the view down), and "N selected" appended to the heading count. **In the card layout (≤ 700px) selecting is an opt-in mode** instead: no checkboxes until "Select" is tapped, then "Select all shown" (standing in for the header checkbox hidden with the header, disabled once everything shown is selected) and "Cancel" in place of "Clear selection" — see "Narrow widths" in `.claude/rules/frontend.md`. **Any route-query change clears the selection** (and ends the card layout's select mode) — the query holds only filters, and a selected-but-hidden row would make a bulk action touch more than the user sees. The day-order chevrons hide while selecting.
  - **Agreed design for the rest:** an opt-in dialog (per-field "change this field" switch, so "leave alone" and "clear" are distinct) over cabin class, aircraft type, airline code, flight number, registration, origin, destination; origin/destination may not be cleared (required). Airport fields get a live resolve preview (needs `GET /api/v1/airports/resolve`) warning when N legs would lose their code. A successful apply clears the selection. No undo for bulk edit; `showUndo` (deferred commit) is for a later bulk delete.
  - **Step 2 landed: `POST /api/v1/flights/bulk-update`** `{ids, changes}` → `FlightService::bulkUpdate`. Patch semantics (present key = set, null clears; absent = untouched), keys whitelisted in `BULK_KEYS` (the seven agreed fields, aircraft as `aircraftTypeRaw` free text *or* a `aircraftTypeCode`+manufacturer+model pick), origin/destination may not be cleared. Every id is looked up before any write, so a foreign id fails the batch untouched; writes share one transaction via `FlightMapper::transactional` (the mapper owns `TTransactional` because the OCP stubs can't mock `IDBConnection` without Doctrine). **It is deliberately not a loop over `update()`**, which rewrites the whole row from its input: merging stored codes in takes the explicit-code branch (coordinates dropped → `distance_km` wiped; a stale aircraft code pinned over edited text), and nulling them instead makes a code-only endpoint (restored backup, no label) fail validation. `applyBulkChanges` touches only the changed fields, reusing `resolveEndpointForUpdate` (the untouched side passes its own label → preserve path) and `resolveAircraftForUpdate`. Two aircraft rules differ from single edit: a pick keeps **each leg's own** `aircraft_type_raw`, and an explicit clear (`aircraftTypeRaw: null`) nulls all four columns rather than hitting the "raw unchanged → keep type" rule, which would keep the type on a code-with-no-raw leg.
  - **Step 3 landed: `components/BulkEditDialog.vue`**, opened from "Edit N flights…" in the selection action bar, covering cabin class, airline code, flight number and registration. Fields are a `FIELDS` descriptor list (key, label, `display` for the "Currently: Economy ×3, Business ×2" summary), so aircraft and origin/destination slot in as further entries with their own editors. Sends only switched-on keys, trimmed, empty → null; the store's `bulkUpdate` swaps the returned rows in by id. The view clears the selection on the dialog's `saved` event, and its Esc-clears-selection handler is suppressed while the dialog is open (that Esc closes the dialog). Error toasts go through `ocsErrorMessage` (see the conventions in `CLAUDE.md`).
  - **Step 4 landed: aircraft type in the dialog**, mounting `AircraftTypeField`. A pick sends only `aircraftTypeCode`/`aircraftManufacturer`/`aircraftModel` — **no `aircraftTypeRaw`**, so each leg keeps its own typed text and whatever was typed in the dialog is treated as a search, not data. Free text sends `aircraftTypeRaw` for per-leg reconciliation; empty sends `aircraftTypeRaw: null` (full clear). The hint line names which of the three paths Apply will take. The summary uses `aircraftDisplay`, so types are named as in the Aircraft column.
  - **Step 5 landed: origin and destination**, the dialog now ordered as the flight editor. Backed by `GET /api/v1/airports/resolve` (`AirportApiController::resolve`, mirroring the aircraft endpoint: `{match: {code, name} | null, referenceLoaded}`) and `components/AirportResolution.vue`, which also emits `update:kind` so the dialog knows when the text won't resolve. On `unmatched`/`noReference` an `NcNoteCard` warns "N of M flights will lose their origin airport code and distance" — a warning, not a block, since an unresolvable free-text endpoint is legitimate. **The count mirrors the server**: only flights with a code on that side, and not those whose stored label already equals the new text (`resolveEndpointForUpdate` keeps their code). An enabled-but-empty endpoint disables Apply, because the server would reject it. **Apply also waits for each switched-on endpoint's preview to settle on the text now in the field**: `AirportResolution` drops its previous result (to `checking`) the moment the text changes, not when the debounce fires, so new text can never be applied under an old "Matches …" with no warning shown. A failed lookup (`error`) counts as settled — it warns that the code *may* be lost rather than locking the dialog.

## View filtering

- **View filtering** (`src/filters.ts`): the filter model is shared by the Flights and Map views so both interpret the route query identically. `buildFilters(query)` → `ActiveFilter[]` (each with `id`, `label`, `queryKeys`, `matches`); `applyFilters(flights, filters)` applies them (AND). The airport filter uses query keys `airport` + `airportDir` (`to` | `from` | `either`) — **both** are required; `airport` alone is only a Map focus hint, not a filter. The single-flight filter uses query key `flight` (an id) — set by the "View on map" item in each flight's row menu. Four filters exist for Analytics' drill-through and have no `FilterPicker` editor: `weekday` (CSV of `mon`…`sun`, from the date's calendar parts via `dateParts`, so timezone-proof), `distanceMin`/`distanceMax` (whole km, min inclusive, max exclusive, either optional; legs without a distance never match), `manufacturer` (CSV, the reconciled `aircraftManufacturer`) and `registration` (CSV, trimmed, case-insensitive). The route filter uses `routeA` + `routeB` + `routeDir` (`ab` directional | `both`) — set by the arc popup on the Map view. The date filter has two `FilterPicker` entries: "Date: custom range" opens the From/To editor, and "Date: current year" commits the device's calendar year directly via `yearRange` (so it is the same range Analytics' Period picker shows as that year), replacing any range already applied and hidden while that year is active. Three toggle filters (set by the `FilterPicker` menu, query value `1`) carry no editor: `unmatchedAirports` matches legs missing either airport `_code`; `unmatchedAircraft` matches legs with no `aircraftTypeCode`; and `multiday` matches legs on any date with more than one flight (offered only when such a day exists; its multi-day set is derived from the full list, so it keeps whole days intact — and `ViewFlightLog` therefore still allows within-day reordering when `multiday` is the *only* active filter). Both round-trip to the Map view like every other filter (shared model + the cross-view buttons carry the full query). On the Map the `unmatched` filter simply shows no arcs — partial legs need both endpoints to draw a line — but any *matched* endpoint of those legs still plots as a marker, a deliberate visual cue for spotting data to fix. The two "Unmatched …" items are each gated on **their own** reference table being non-empty, probed once on mount via `Promise.allSettled([listAirports, listAircraftTypes])` — the tables are imported independently, so one loaded table must not light up the other's filter, and a failing probe must not take the other down with it. `unmatchedAircraft` matches `!f.aircraftManufacturer || !f.aircraftModel` — every leg whose Aircraft column cannot show "MANUFACTURER Model". That deliberately covers three shapes as one worklist: nothing entered, entered but unresolved, and **half-reconciled** (a designator with no manufacturer/model, which a JSON restore produces by honouring a stored code without resolving it). It was previously keyed on `!f.aircraftTypeCode`, which missed that third shape entirely — those legs have a code, so they were invisible here *and* excluded from the Aircraft types flown list, with nothing anywhere to reveal them. Keying on the pair also makes the two views agree on what "resolved" means. The aircraft filter's `[blank]` sentinel still isolates the entered-nothing case alone. The airport key was renamed from the bare `unmatched` to `unmatchedAirports` in 1.0.8 for symmetry — a filter URL saved before that no longer applies the filter (it is ignored, not mis-applied).

New filter types extend `buildFilters()`; the chip row and clearing are generic over the shape. Both views show removable `NcChip`s for the active filter plus cross-view buttons that carry the query across — "View on map" (`ViewFlightLog` → `/map`), "View in log" (`MapView` → `/flights`) and "View analytics" (both → `/analytics`, which shows the same chips, except that a single-year date range is shown by its Period picker instead).
