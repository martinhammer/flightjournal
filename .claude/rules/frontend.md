# Frontend

## Narrow widths

Usable from 360 px (CSS) up.

- **`.fj-view`** (`src/styles/views.css`, imported once from `main.ts`) is on every routed view's root (MapView: its header). It owns the view padding and seats the first `h2` *beside* the navigation toggle (☰), which floats over the content's top-left corner at every width — so the rule applies on desktop too. Don't re-add per-view `padding: 16px`.
- **Two width steps per table, as viewport media queries** (no container queries: there is no sidebar). *Medium* `701–1100px` hides the least-scanned columns (`th` and `td` by the same `nth-child`, so headers stay over their columns). *Cards* `≤ 700px`. The ranges are exclusive so the card rules never undo a medium hide. **700 lives in two places that must change together:** `CARD_BREAKPOINT_PX` in `src/useCardLayout.ts` (a `matchMedia` ref for script decisions) and the CSS `@media (width <= 700px)` blocks, each commented to point at the other.
- **Cards are the same `<table>` restyled, never a second `v-if` list.** Each `<tr>` becomes a wrapping flex line of its cells, reordered with `order` into lines, the row's `::before`/`::after` (`flex-basis: 100%`) acting as line breaks; checkbox and row menu are absolutely placed in the row's side padding. An unset value must render `''` so its cell is `:empty` (hidden), and the `·` separators are generated only between set values by sibling selectors. Any zero-basis item would sit beside a line break instead of after it — hence the aircraft cell's `flex-basis: 1px`. Because changing `display` can drop table semantics, the tables carry **explicit ARIA roles** (`table`/`rowgroup`/`row`/`columnheader`/`cell`). Counts read "N flights" from a `data-unit` attribute via CSS, leaving the cell text the bare number the specs assert.
- **Add flight in card mode:** the navigation's entry is behind the toggle on a phone, so `ViewFlightLog` adds a primary "Add flight" button at the end of the heading line, only when `useCardLayout()` is true; the navigation entry stays at every width. Both set `addFlightOpen` (`src/addFlight.ts`), which opens the one `AddFlightDialog` rendered in `App.vue`. The button is absolutely placed in `.view-flight`'s top-end corner rather than wrapped with the `h2`: a wrapper would lose the `.fj-view > h2:first-child` seating beside the toggle and stop the `h2`'s margin collapsing with `.filter-bar`, shifting the desktop layout.
- **Flights in card mode:** the header is hidden, so sorting moves to **`components/SortMenu.vue`** (an `NcActions` of radio items over the view's `columns`, emitting the key to the view's own `setSort`, so re-picking the active column reverses it). **Selecting is a mode** (`selectMode`, spec D7): by default no checkboxes render and the card takes the full width; a tertiary "Select" button beside the sort menu turns it on, and the action row then shows "Edit N flights…" (once something is selected), "Select all shown" and "Cancel" (leaves the mode and clears; replaces "Clear selection", which the desktop table keeps). Every path that clears the selection — filter change, successful bulk apply, Esc, "Cancel" — goes through `clearSelection()`, which also ends the mode; a selection carried into the card layout (rotation) arrives in the mode. **A tap opens Edit** with the current query; **in select mode a tap toggles** the row instead (Mail-style) — keyed on the mode, not on whether anything is selected; taps on the checkbox and ⋮ cells keep their own meaning, and a double tap does nothing (it would toggle twice, then edit). Double-click-to-edit stays desktop-only. The reorder chevrons are hidden; **"Move up/down within the day" items in each row's ⋮ menu** call the same `move()` and are shown at every width (also a keyboard path).
- **Hover styling is wrapped in `@media (hover: hover)`** so a tap can't leave it stuck; `:focus-visible` and active states stay unconditional. Map arcs and markers bind hover tooltips only under `(hover: hover)` — their click popups repeat the same lines — and popups auto-pan clear of the zoom control.
- Nextcloud core styles some bare class names globally (`.pager` is floated with a 13em end margin) — prefix generic layout classes with `fj-`.

## Frontend tests (Vitest + type-check)

- **Type-check:** `npm run type-check` (`vue-tsc --noEmit`) is a gate — wired into `make lint`. It catches `@nextcloud/vue` v8→v9 prop/event mismatches. `src/shims-icons.d.ts` declares the `vue-material-design-icons/*.vue` modules (the package ships `.d.vue.ts` files but no `exports` map).
- **Component tests:** Vitest + `@vue/test-utils` under `tests/frontend/` (`*.spec.ts`), config in `vitest.config.ts`, shared mocks in `tests/frontend/setup.ts`. Run via `npm run test:frontend`, gated through `make test`. `@nextcloud/vue` is inlined (`server.deps.inline`) so Vite handles its CSS side-effect imports.
- **Add a component test for every new interaction-critical UI path** (form save, search, filter, destructive action). Test the wiring as a user drives it — stub heavy children but emit the real model event / click the real button so a wrong prop or event name fails the test. When mounting a real `@nextcloud/vue` component, mock `vue-router` with `importOriginal` so injected keys (`routerKey`) survive. `AdminSettings.spec.ts` covers both reference tables through the shared `ReferenceDataSection`; since one component drives both, its assertions are mostly that each instance is aimed at *its own* endpoints — a wrong `basePath` would import aircraft into the airport table or wipe the wrong one.
